Armada × Laconic

Two additive offers for Armada's shielded pool: more yield and the mobile-first private support services that surround it. Armada builds the crypto core; Laconic provides the added yield and the private substrate around it.

for: Armada team non-custodial pool untouched Ethereum L1-anchored status: proposal + code-fit map

Armada is pluggable asset-privacy infrastructure for USDC: a shielded pool (Railgun ZK circuits, immutable), governance-added adapters (CCTP, Aave v4 yield, swaps), and an apps/SDK tier, funded by integrator revenue-share. This site proposes how Laconic slots into that model — as new yield sources and as the private, mobile-first substrate the pool depends on. Companion docs: the thesis (why Laconic is the substrate) and the ex_net whitepaper (the 2017 design ancestor).

The two offers

1 · More yield

A private execution/settlement platform that sits beneath Armada's Adapters tier and powers the yield & swap adapters.

  • Native yield — LP spread + swap/routing fees earned in the venue, an additional yield source alongside Aave v4.
  • Private rail — non-custodial movement of idle shielded balances into external yield (Aave v4) and back, with metering, accounting, and settlement.
  • Engine: the ex_net → matcher — a frequent-batch-auction, curve-order matcher that unifies CLOB + RFQ, capital-efficient, non-custodial.

2 · Support services

The private, mobile-first substrate that runs Armada on phones and browsers with almost no fixed infrastructure.

  • Private sync — proof-carrying note streams that protect the anonymity set at read-time (Armada's core fragility: it dies at read-time over normal RPC).
  • Metering — pay-per-request Nitro vouchers.
  • Mobile client + relay — the Laconic wallet (Android/iOS/web) + in-browser Nitro node + libp2p relay.
  • Deploy / ops — bonded service-provider federations run it; monetized via Armada's integrator revenue-share.

How it plugs into Armada

ex_net is not a sibling adapter — it is the private execution/settlement platform beneath the Adapters tier. Armada's Swaps and Aave-v4 yield adapters become applications built on it; future governance-added adapters run on the same substrate. The shielded pool stays immutable and untouched; the platform operates at the adapter/execution tier, non-custodially.

Honest scope notes

  • Shared substrate ⇒ its own audit boundary. Putting ex_net under multiple adapters makes it a shared dependency — a larger surface than one independently-deployed adapter, and it needs its own audit. Worth stating plainly against Armada's "each adapter independently deployed & audited" discipline.
  • Pool stays immutable. ex_net operates at the adapter/execution tier; nothing here alters Armada's core contracts or takes custody.
  • Depth is uneven. Only the execution platform (ex_net → matcher) has been validated in depth so far; the rest is design-level / net-new. The Build plan marks per-component confidence.
