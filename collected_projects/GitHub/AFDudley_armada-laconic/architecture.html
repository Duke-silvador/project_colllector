Architecture — the tier stack

A mobile-first, non-custodial, front-running-resistant private execution platform, delivered through bonded Laconic watcher parties beneath Armada's Adapters tier. Seven tiers, each mapped to existing code where it exists.

non-custodial Ethereum L1-anchored pool immutable / untouched

Tiers are named in the software-architecture sense (an n-tier stack) — deliberately not the "Layer 1 / Layer 2" of blockchains. Every claim maps to code on the Build plan (with pinned commits and status). This page is the structure; the build plan is the status + backlog. Code links use GitHub where a mirror exists, otherwise the canonical Laconic Gitea (git.vdb.to).

The shape of the network — mobile-first

The central requirement: every service is delivered through watcher parties so the overwhelming majority of the network is browser wallets and mobile apps talking peer-to-peer. The only fixed infrastructure is (a) a handful of STUN/TURN servers for NAT traversal and (b) a small number of plugeth-based Ethereum state injectors that feed L1 state into the parties. Everything else — sync, metering, matching, settlement, threshold attestation — is run by the bonded service-provider federations and the clients.

Clients hold their own keys and funds (channels are L1-collateralized); a watcher party never takes custody and can be exited unilaterally. The two boxes of fixed infra are deliberately small — STUN/TURN carry no trust, and plugeth injectors only publish verifiable state.

T0 · Ethereum anchor — settlement & shielded custody

Settlement is non-custodial Nitro state channels on Ethereum L1. Funds are locked in the NitroAdjudicator / MultiAssetHolder and allocated off-chain by co-signed state; a channel closes cooperatively at internet speed, or unilaterally via the ForceMove dispute game — challenge, checkpoint, conclude[5]. This is the escape hatch that makes the venue safe: if a party misbehaves, the user force-closes to their last co-signed state; no settlement receipt ⇒ force-close returns the pre-fill deposit. The adjudicator only ever honors user-signed states, so a byzantine federation can stall you but cannot fabricate balances or move unsigned funds. 

contract HashLockedSwap is IForceMoveApp {
    struct AppData { bytes32 h; bytes preImage; }   // reveal preimage of h to unlock
    ...
}

source: go-nitro · HashLockedSwap.sol#L11–L33

Cross-chain / L1↔L2 movement reuses the Bridge mirrored-channel construction[10]. What's built here: the Railgun shielded pool (Armada's, immutable) and the full Nitro adjudicator/ForceMove/MultiAssetHolder[5], live on Ethereum. What's net-new here: a venue/party registry + bond contract, an on-chain sequencing-cert + fraud-proof verifier, and the Nitro↔Railgun boundary adapter (see Privacy). Full status on the Build plan.

T1 · Ingestion (plugeth → watchers)

The mechanism that gets L1 state into the watcher parties: Vulcanize's plugeth[16] + plugeth-statediff[17], which extract full Ethereum state diffs from a geth node without forking geth, and the IPLD services that index and serve it — ipld-eth-server[18] and ipld-eth-state-snapshot[19].

This is what makes private sync possible: a watcher party ingests the Railgun shielded-pool commitments/nullifiers and the Nitro adjudicator events via plugeth, then serves proof-carrying, identical-for-everyone note streams metered by Nitro. Clients scan those streams locally, so no RPC provider ever fingerprints a user against the pool — the single property Armada's anonymity set depends on. A few injectors serve the whole network; the phones and browsers do the rest. The generic watcher-ts framework[2] exists; the Railgun/adjudicator-specific watcher config is the integration work.

T2 · Watcher-party substrate

A watcher party is a bonded federation of service providers that collectively serves one data need — the "Federated Cache" role in Laconic's Service-Provider Marketplace. Here it is also the execution venue: it delivers all of Armada's private support services at once.

ServiceDelivered by the watcher party as…
Private shielded-pool syncfederated cache serving proof-carrying, everyone-gets-the-same-bytes note streams (clients scan locally & privately)
Metering / paymentsper-request Nitro vouchers[8] over virtual channels[9]
Matching / venuecommit-reveal sequencing + a matcher over revealed orders (T3–T4)
Attestationthreshold-Schnorr (DSS) inclusion receipts, sequencing certs, liquidity-proof snapshots
Membership / bondingan on-L1 registry + bond; disputes and slashing settle on L1 (T0)
Why "party," not "chain": the federation only needs to (a) agree on which commitments are in an epoch and (b) fix an order — a sequencing-and-attestation task, not replicated global execution. That is a far weaker (and cheaper) primitive than BFT consensus, and it is what lets the network live on phones.

The federation signature — threshold Schnorr (DSS)

The party signs everything it attests to with a threshold Schnorr signature: the chain-signatures library — Ethereum-compatible Schnorr (ethschnorr.Sign / Verify)[12] and the Distributed Schnorr Signature protocol (Stinson & Strobl (t, n)) in ethdss[13], built on a kyber DKG. Two properties matter:

  • On-chain verifiable. Because it is Ethereum-flavoured Schnorr, an L1 contract can verify a party's aggregate signature — so a sequencing cert or a censored-commit receipt becomes a slashable fraud proof against the bond (T0).
  • Threshold direction is safety-first. t-of-n tolerates t−1 malicious for safety, n−t offline for liveness. We pick t high (e.g. 4-of-7) so forging an attestation needs a large coalition; liveness failure degrades to halt, not loss because settlement is non-custodial. (A BFT-style small quorum like 3-of-11 would be wrong — it would let any 3 forge.)
The threshold key is used for signing only. We do not run a threshold-encrypted mempool — with the sequencer and key-holder being the same federation, encryption gives no real fairness (a colluding threshold can decrypt-then-order). Fair ordering is achieved with commit-reveal instead (T3).

T3 · Ordering & fault model

Fair ordering = commit-reveal

Orders are hidden from the venue during ordering with commit-reveal, not client-side ZK: a phone generating a SNARK per order costs seconds, whereas a reveal round-trip is tens of milliseconds, and the user is already interactive through settlement. Flow: commit = H(order ‖ salt) → the party seals the epoch and emits threshold-signed inclusion receipts (so censorship is slashable) → a post-seal randomness beacon fixes positions → the user reveals → the matcher runs over revealed orders in the fixed order. The party cannot content-front-run (it only saw hashes) or position-manipulate (the beacon is post-seal). ZK order submission remains an opt-in for offline submitters or server-side provers.

Latency & receipts

A cooperative fill is 3 RTT + Δ (commit, reveal, settle) with Δ ≈ the party's co-located sealing window (single-digit ms). Settlement is one round trip whose two legs are both mandatory: the user signs first, the venue returns a bond-enforced settlement receipt. There is no fire-and-forget — every fill terminates in either a co-signed receipt or a slashable proof of its absence.

Griefing is a non-issue here

Because the venue is the one providing asks, a user who withholds a reveal harms no third party — the ask is a standing quote available to all, so a non-revealed commit blocks no other user's liquidity. Turn-by-turn, the only theoretical residual is a sub-second free option on a stale quote, worth ~nothing as long as the reveal timeout ≤ the quote-repricing interval (a knob the venue controls). Anti-griefing collapses to a nominal anti-spam commit fee.

Failure = halt, not loss

If the party stalls or drops below its liveness threshold, users force-close to their last signed state and are made whole; a watchtower guarantees the latest state even for an offline user. Non-custody means a dead party freezes trading, never funds.

In Ethereum terms this tier is a decentralized sequencer + DA + fraud-proof ordering over state-channel settlement — not a rollup (there is no shared L2 state root; balances are enforced by the channel adjudicator). See the Build plan — this is the highest-design-risk, mostly net-new tier.

T4 · Execution / settlement platform (ex_net)

This is the platform that Armada's adapters run on. The matcher is a frequent-batch-auction, curve-order, filler-filtered CLOB/RFQ hybrid that prices, matches, and settles privately into Nitro channels. It is covered in depth on its own page — Execution platform — including the ex_net lineage, the 2019–2020 matcher PoC, capital-efficiency vs. AMMs, and how Swaps and yield become applications on top. Settlement reuses go-nitro's multi-asset swap protocol[6] and SwapChannel[7]; the net-new pieces are the LP/market-maker vault, receipt-or-slash wiring, and multi-asset outcomes.

T5 · Adapters (Armada's tier)

Armada's Swaps and Aave-v4 yield adapters are applications of the T4 platform, not peers to it. The Swaps adapter is a thin integration exposing "swap shielded A→B," with the matcher doing the matching + channel settlement underneath. The yield adapter uses ex_net as the private rail into Aave v4 and as a native yield source (LP spread + fees). CCTP (cross-chain USDC) is Armada's, already built. Future governance-added adapters run on the same substrate. Nothing here touches the immutable pool.

Audit boundary. Positioning ex_net under multiple adapters makes it a shared dependency with its own audit surface — a larger ask than one independently-deployed adapter, and a deliberate deviation from Armada's "each adapter independently deployed & audited" discipline. Stated plainly so it is designed for, not discovered.

T6 · Client / apps (mobile-first)

The client is the Laconic wallet — a React Native app on Android and iOS[21] (with a browser build[22]): it custodies keys and signs both Cosmos and EIP-155 requests over WalletConnect, and pairs with an in-browser / mobile Nitro node[4] for payments and a libp2p relay. This is the mobile-first shape the MobyMask stack[3] already proved end-to-end (app-specific signing + in-browser Nitro + p2p relay to a keeper). Net-new: wallet updates (return pubkey on cosmos_signAmino, Nitro + commit-reveal integration, Railgun boundary UX) and the Armada SDK integration.

Cross-cutting · Identity

Deliberately thin and privacy-first, described by two existing pieces of Laconic work.

ex_net identity proofs

ex_net[1] defines the primitive: a user links an external key to their trading identity by signing a message with the external private key that embeds their venue public key, and — in its forward-looking form — can prove a match (e.g. passport ↔ liveness) and record only the proof, never the underlying data. Identity is an optional, user-initiated, selectively-disclosed proof beside the shielded default; the venue stays identity-blind unless a counterparty or jurisdiction requires a proof. The shipped precedent is laconicd's onboarding module, whose on-chain Participant record carries role and kyc_id[14].

The Laconic Matchmaker

The Laconic Matchmaking Services proposal[15] supplies the compliance-gating half: a privacy-preserving matchmaking service that pairs technically-qualified operators with capital backers "in a way that's compliant with international broker-dealer laws and respects their users' privacy," implemented as encrypted computation that matches number ranges and finds intersections of number intervals. In exchange terms: the matcher can verify that two parties satisfy each other's constraints (jurisdiction, accreditation, size band, KYC status) without either party — or the venue — learning the other's identity or exact values. Underlying FHE / encrypted-computation is an implementation detail; the design depends only on the two abstractions above.

Cross-cutting · Privacy boundary (Design A)

Privacy is delivered by funding and settling channels through a Railgun-style shielded pool via an adapter[20] — the same adapter pattern Armada already uses, with a Nitro adapter added. The venue's visibility begins at the shield boundary and never reaches behind it: it sees the shielded-side order terms it must match and an ephemeral channel identity, but not who you are, where the funds came from, your on-chain history, or that two trades were the same person. The venue is a blind, non-custodial matcher.

Caveats: identity privacy is only as strong as the Railgun anonymity set and is subject to amount/timing correlation (mitigate with denominations/batching and a fresh per-channel identity). The only thing still visible to the venue is the trade's amounts/terms — hiding those too is Design B (ZK matching + a "shielded ForceMove" dispute over hidden state), out of scope for v1.

Namada is not Design B. Namada's MASP is an excellent multi-asset shielded-note primitive, but Namada is an L1 with global consensus — not a state channel — so it has no off-chain, non-custodial, unilateral exit and runs at chain speed. It attains privacy the way ex_net attained fairness: with a chain. MASP-the-circuit could serve as a note primitive for a future Design B; Namada-the-chain does not provide the channel-speed exit this design requires.
