Matt Pocock 的 AI 开发全流程

从一个想法开始，经过 5 步，到代码提交——30 万 Star 技能仓库作者的完整主流程。

来源：小红书 @unintended.ai《30w Star 项目作者的 AI 编程工作流》 · 共 5 步 · 每步一个 skill

Matt Pocock 的 skills 仓库有 30.6 万 Star、3060 万次下载，但一直没有教程。最近他录了第一个完整的主流程演示：从一个想法开始，经过 5 步，到代码提交。具体技能可能会换，但他每次做的事情没变：先花 token 把需求聊清楚，按 140K 的预算切好工作量，最后用没写过这段代码的 agent 来审。

需要的东西很简单：一个本地 Agent，比如 Claude Code、Codex、WorkBuddy。一行命令安装：

npx skills@latest add mattpocock/skills

装完跑 /setup-matt-pocock-skills，配置三样：issue tracker（GitHub Issues、Jira、Linear 或本地 Markdown 都行）、分诊标签（默认就好）、领域文档（单上下文，99% 的项目够用）。

01主流程的五步

38 个技能分两组：Matt Pocock Skills 是他认可的正式技能，Other 是实验中的。几乎全部是用户主动调用——你打命令它才加载，不打就不占上下文。38 个技能只占 660 个 token，因为技能描述被压到最短，需要时才展开。很多别的 skills 仓库一装上来就往系统提示词里塞一大堆描述，这是他刻意避开的做法。

1
/grill-with-docs

动手写代码之前，先跟 AI 对齐理解。整个流程的起点，也是 Matt 认为最关键的一步。

2
/to-spec

把当前窗口的所有讨论压缩成一份终态文档。

3
/to-tickets

把 spec 拆成一张张可执行的工单，每张 = 一个上下文窗口的工作量。

4
/implement

写代码，跑完整验证：type check、build、测试。

5
/code-review

用独立的子 agent 审查，不让写代码的 agent 自己说了算。

02Grill with Docs：先对齐，再动手

用法很简单：输入 /grill-with-docs，加上一个粗略的想法。Matt 演示里的输入是"我想删掉这个 CLI 里大部分内部工具，只保留面向公众的功能"。就这么模糊，不需要更多准备。

接下来 agent 主导。它先扫描整个代码库，搞清楚现状（比如发现 internal 命名空间下有 11 个子命令），然后开始结构化追问。每个问题都指向一个具体的决策点：这 10 个命令哪些要删？共享模块会不会被连带影响？agent 的开发脚手架要不要一起清掉？

Matt 这次只被问了 6 个问题就结束了；他说通常会有 20 个左右，取决于任务复杂度。关键不在问题数量，而在结束条件：双方都认为已经达成了共同理解（shared understanding）。agent 最后还会主动确认："我们是不是达成了共同理解？可以开始执行了吗？"

最终产出是一份明确的计划：删除 10 个命令文件、删除 3 个测试、重新连接共享模块、移除 5 个依赖、删掉 sandcastle 工具链。每一项都是具体的文件和操作。

03岔路口：一个窗口做完，还是拆成多个

grill 做完，这个上下文窗口已经用了 46.1K tokens。判断依据是 Matt 说的 smart zone：他认为 LLM 在上下文超过大约 140K tokens 之后会明显变笨——注意力退化，开始出现幻觉。140K 以内是 smart zone，在这个范围里 agent 的输出质量是稳定的。

grill 已用 46.1K 剩余预算 约 100K（smart zone 上限 140K）

判断方式很直接：剩余预算够不够把活干完？Matt 看了一下任务量——删 10 个命令——觉得绰绰有余，正常情况下他会直接输入 /implement this，让 agent 一口气做完（这个任务的 implement 阶段实际只用了 42.7K tokens，属于轻量任务）。但为了演示完整流程，他选择了走 spec + tickets 的路线——这条路线是为那些一个窗口装不下的大任务准备的。

04Spec + Tickets：把理解压缩好，跨窗口传递

/to-spec 把之前 46.1K tokens 的对话——包括你回答的每个问题、双方确认的每个决策——浓缩成一份 spec。这份 spec 描述的是"做完之后应该长成什么样"：问题陈述、解决方案、用户故事、实现决策、测试决策、明确不做的范围，都在里面。

/to-tickets 再把 spec 拆成一张张可执行的工单，每张工单的大小 = 一个上下文窗口（smart zone）能完成的工作量。Matt 这次演示里 agent 给了 3 张工单，他觉得太多了，1 张就够，让 agent 改成 1 张。

他展示了一个真实的大任务拆分：几天前的一份 spec，下面挂了 11 张工单。每张工单内容很短，因为验收标准已经在主 spec 里了，工单只回答一个问题：这一轮会话里你要做什么。

执行时一张一张来。做完一张，清掉上下文（/clear），开始下一张。每张工单从干净的窗口启动，加载 spec 和当前工单作为上下文，在 smart zone 内完成工作。

这就是 spec 和 tickets 存在的原因：grill 阶段花大量 token 建立的共同理解，不能因为清上下文就丢掉。Spec 是压缩后的共识载体，tickets 是按窗口容量切好的执行单元。

05Implement + Code Review：执行，然后换人审查

所有工单做完——或者 grill 完直接走 implement 的情况下——输入 /implement，agent 开始写代码。Implement 技能会做完整的验证：跑 type check、跑 build、跑测试。验证通过后，它会自动启动 code review，而且用的是独立的子 agent，不是刚才写代码的那个。

Matt 解释了为什么这么做：agent 审查自己刚写的代码效果很差。因为代码是它自己写的，它倾向于觉得没问题，不会认真找毛病。但如果另起一个干净的上下文窗口，新 agent 没有写代码时的心理惯性，审查质量会好得多。

Code review 按两个维度展开，两个子 agent 并行跑：

  • 对照 spec 逐条验收：检查实现是否覆盖了 spec 里的每一条要求。Matt 说这在大任务里特别有用，因为 agent 可能漏掉工单里的东西，或者工单本身就写得不够明确。
  • 对照编码规范检查代码异味：如果仓库里有编码规范文档就用你自己的，没有的话会用一套经典规范。

Matt 的演示里两个维度都通过了，代码直接提交到当前分支。

06什么时候走全流程，什么时候跳步

这套流程不是每次都要从头到尾走完，判断标准很简单：

小任务

grill → implement this

grill 完估算 token 预算够用，直接 /implement this，跳过 spec 和 tickets。删命令这个任务的 implement 阶段只用了 42.7K tokens，就是轻量任务。

大任务

grill → spec → tickets → 逐张 implement

一个窗口装不下的，走完整路线。每张工单之间清上下文，保证 agent 始终在 smart zone 内工作。

不变的是前后两端：前端永远是 grill——在写代码之前跟 AI 建立共同理解；后端永远是 code review——用独立 agent 审查，不让写代码的 agent 自己说了算。中间的 spec 和 tickets 可按任务大小增删。
