1. Ziel & Prinzip

Die Landingpage soll Modelle verständlich und verkaufsnah zeigen — nicht den kompletten AI Hosting Bench. Später kommen alle Modelle über eine API. Bis dahin reichen lokale JSON-Fixtures mit identischem Schema.

Faustregel Wenn ein Feld bei (fast) allen Modellen gleich ist → catalog. Wenn es sich mit dem Modell ändert → models/{id}.json.

2. Architektur: Catalog vs. Modell

Catalog (gemeinsam)

1× laden, cachen, wiederverwenden

  • Benchmark-Metadaten (Name, Blurb, Kategorie, URLs)
  • Dedicated-Tiers (VRAM, Labels)
  • Taxonomy (Tags, Badges, Capabilities)
  • Globaler Quantisierungs-Hinweis
  • schema_version

Modell (individuell)

pro Modell / Detailseite

  • Identität, Specs, Creator
  • Pitch, Tags, Badges, Hosting-Fit
  • scores + scores_updated
  • highlights (nur key + value)
  • CTAs, Alternativen, i18n-Texte
Nicht im Modell wiederholen Lange Benchmark-Descriptions und Blurbs gehören in den Catalog. Die Landingpage joined highlights[].key → catalog.benchmarks[key].

3. Endpoints (Ziel-API)

So soll die spätere API aussehen. Fixtures spiegeln dieselbe Struktur.

Methode Pfad Zweck
GET /v1/catalog Benchmarks, Tiers, Taxonomy, Meta-Hinweise
GET /v1/models Liste (leicht): id, display_name, badges, tags, hosting.shared, highlights
GET /v1/models/{id} Volles Modell-Objekt für Detailkarte / Modal
catalog + models[] → Landingpage UI

5. Was die Landingpage rendern soll

Pro Modell-Karte / Abschnitt — bewusst schlank:

  1. Titel: display_name + Creator-Name (Logo wenn vorhanden)
  2. Pitch: pitch (1 Zeile)
  3. Badges: z. B. Shared / Vision / Empfohlen
  4. Specs-Zeile: Params · Context · License · VRAM INT4
  5. Hosting-Fit: „Passt auf L+ / XL“ aus hosting.comfortable_tiers
  6. 3–5 Highlights: Score + Blurb aus Catalog (nicht 40 Spalten)
  7. Hinweis: globaler Quantisierungs-Text aus Catalog-Meta
  8. CTAs: Modell nutzen · Im Bench vergleichen
Nicht auf der Landingpage Komplette Score-Matrix, OpenRouter-Preise als Hauptpreis, interne Index-Rohwerte ohne Erklärung. Tiefe → Link zum AI Hosting Bench.

6. Felder im Modell-JSON

Feld Pflicht Verwendung auf der Website
id / slug Muss Stabile ID, Routing, API-Key
display_name Muss Sichtbarer Modellname
creator Muss Anbietername, optional Logo/URL
params, context, license Muss Specs-Zeile
capabilities Muss Vision/Tools/… Icons oder Chips
vram Muss GPU-Passung; bevorzugt int4 anzeigen
hosting Muss Shared-Flag, API-Model-ID, passende Tiers, Docs-Link
lifecycle.status / .label Muss Portal-Status: LTS · Stable · Testphase
token_factor / token_factor_label Muss Verbrauchsfaktor Shared (z. B. 0,5x / 1x / 1,5x / 3x)
pitch / short_description Muss Marketing-Text (kurz / etwas länger)
tags / badges Muss Filter & visuelle Marker
highlights[] Muss 3–5 Scores für die Karte (key + value)
scores / scores_updated Muss Rohdaten; Detailansicht / spätere Filter
cta Muss Primary/Secondary Buttons
not_ideal_for Soll Erwartungsmanagement
alternatives Soll „Ähnliche Modelle“
mittwald_pricing Soll Eigene Preise (nicht OpenRouter als Default)
i18n Soll DE/EN für Pitch & Description
ranking / performance Später Platzierungen, Tokens/s — oft noch null
updated_at Muss „Stand: …“ / Cache-Busting

Beispiel: Highlight (schlank)

{
  "highlights": [
    { "key": "aa_coding_index", "value": 68.1, "updated": "2026-08-25" },
    { "key": "deepswe", "value": 42.2, "updated": "2026-08-15" },
    { "key": "mmmu_pro", "value": 76.3, "updated": "2026-08-17" }
  ]
}

Label/Blurb kommen aus dem Catalog — nicht hardcoden, außer als Fallback.

7. Felder im Catalog

BlockInhaltUI-Nutzung
meta schema_version, score_precision.note Fußnote unter Scores
tiers[] id, label, vram_gb, bookable „Passt auf L“ erklären / Tooltip
taxonomy tags, badges, capabilities Filter-Optionen, Labels
benchmarks{} name, short_name, blurb.de/en, category, urls Highlight-Beschriftung + Tooltip

8. Join-Logik (Scores + Blurbs)

Pseudo-Code für die Landingpage:

const catalog = await fetch('/v1/catalog').then(r => r.json())
const model   = await fetch('/v1/models/qwen3-8-27b').then(r => r.json())

const highlightCards = model.highlights.map(h => {
  const b = catalog.benchmarks[h.key] || {}
  return {
    key: h.key,
    value: h.value,
    updated: h.updated,
    label: b.short_name || b.name || h.key,
    blurb: b.blurb?.de || '',
    href: b.urls?.[0]
  }
})

const footnote = catalog.meta.score_precision.note.de
Fallback Fehlt ein Benchmark-Key im Catalog: Key roh anzeigen, Blurb leer lassen — Seite nicht crashen.

9. Quantisierung & Benchmarks

Es gibt einen Score pro Modell, typischerweise aus BF16/FP16-Läufen. vram.fp16 / int8 / int4 sind separate Speicher-Schätzungen. INT4/INT8 können die Qualität leicht senken — das ist nicht als zweiter Score modelliert.

Bitte den globalen Hinweis aus catalog.meta.score_precision.note unter den Highlight-Scores anzeigen (klein, einmal pro Modul/Seite).

10. Implementierungs-Checkliste

  1. Catalog einmal laden und cachen (Session/SSR).
  2. Modell-Liste oder Detail aus Fixture/API laden.
  3. Karte mit display_name, pitch, badges, specs, hosting-fit bauen.
  4. Highlights joinen (key → blurb/label).
  5. Quantisierungs-Fußnote aus Catalog setzen.
  6. CTA primary = Docs/Nutzung, secondary = Bench.
  7. null-Felder robust behandeln (Ranking, Performance, Preise).
  8. i18n: bei lang=en model.i18n.en + blurb.en nutzen.
  9. Schema-Version prüfen (schema_version) — bei Breaking Changes UI absichern.
  10. Später nur Base-URL auf echte API umstellen; Schema bleibt gleich.

Mini-Beispiel Hosting-Zeile

Qwen3.8-27B · Alibaba
27B · 256k Context · Apache-2.0 · Vision
VRAM INT4 ≈ 15 GB · empfohlen INT4
Shared verfügbar · passt komfortabel auf L+ / XL
Coding 68.1 · Lange Coding-Jobs 42.2 · Vision 76.3
Hinweis: Scores in Standard-Präzision, nicht pro Quantisierung.
